# Genba Webサイト・リニューアル指示書

最終更新: 2026-08-20

関連資料: [09-pivot-business-plan.md](09-pivot-business-plan.md)

## 1. リニューアルの目的

既存サイトは、海外企業向けの英語中心アドバイザリーサイトとして設計されている。これを、日本の外資SaaS営業職向けの無料データメディアへ変更する。

リニューアル後の最重要行動は、問い合わせではなく以下とする。

1. 無料ニュースレターへの登録
2. 企業・求人ページの閲覧
3. 企業公式求人への遷移
4. 採用企業・スポンサーからの掲載問い合わせ

## 2. 実装方針

### 維持するもの

- Next.js 14 App Router
- TypeScript
- Tailwind CSS
- static export
- Cloudflare assets deployment
- Markdownベースの記事管理
- 日英対応可能な基盤

### 変更するもの

- 日本語を主言語にする
- トップページをメディア・データベース型へ全面変更
- Advisory、Services、既存Contact中心の導線を廃止・再配置
- 企業・求人・変更履歴を構造化データで管理
- ニュースレター登録を全ページの主要CTAにする
- 採用企業向けページを追加
- 既存の英語記事はアーカイブとして保持するが、トップ導線から外す

## 3. URL設計

推奨URLは以下。

| URL | 役割 |
|---|---|
| `/` | 日本語トップ |
| `/companies` | 外資SaaS企業一覧 |
| `/companies/[slug]` | 企業詳細・採用タイムライン |
| `/jobs` | 外資SaaS営業求人一覧 |
| `/jobs/[id]` | 求人詳細・公式応募リンク |
| `/insights` | 編集記事一覧 |
| `/insights/[slug]` | 記事詳細 |
| `/newsletter` | 無料ニュースレター登録 |
| `/advertise` | 求人掲載・スポンサー案内 |
| `/en/advertise` | スポンサー案内の英語版 |
| `/methodology` | 情報源・判定・訂正方針 |
| `/about` | Genbaと編集方針 |
| `/contact` | 一般・訂正・掲載問い合わせ |
| `/en/...` | 既存英語記事のアーカイブ候補 |

既存の `/ja` を日本語ルートとして残すのではなく、日本語をルート直下に移す。既存URLから301リダイレクトできないstatic export構成では、旧URLの保持またはHTMLレベルの移行案を検討し、検索評価を失わないようにする。

### 5.3 ソリューション領域別の採用ヒート

- 「どの領域が、いま熱いか」をトップページで企業一覧より先に表示する
- Genba掲載中の確認済み求人を、企業のソリューション大分類別に自動集計する
- 一覧・絞り込み・採用温度では、詳細カテゴリを`AI・データ基盤`、`セキュリティ・IT運用`、`CRM・顧客体験`、`業務自動化・コラボレーション`、`経営管理・FinTech`、`コマース・業界特化`、`HR・人材育成`の7分類へ統合する
- 製品固有の詳細カテゴリは企業詳細ページに残し、大分類と詳細カテゴリを混同しない
- 1社の追加だけを理由に大分類を新設しない。分類体系を変える場合は、全企業の検索体験と集計への影響を確認する
- 領域は`HOT`、`Active`、`Selective`の3層へまとめる。相対値ではなく、現在公開中と公式確認できた日本向け営業求人の件数と、その求人を掲載する企業数による固定基準を使う
  - `HOT`: 国内営業求人20件以上、かつ採用企業10社以上
  - `Active`: 国内営業求人10件以上、かつ採用企業5社以上
  - `Selective`: 国内営業求人1件以上。`HOT`・`Active`の条件を満たす領域は上位区分を優先する
- 各層の見出しには、現在その層に含まれる採用企業数と国内営業求人数を`HOT（10社／20求人）`形式で表示する。固定値ではなく、同じ集計結果から自動更新する
  - 求人0件の領域は3層へ含めず、継続観測とする
- 各カード全体から、その層の大分類に属し、現在日本向け営業求人を1件以上確認できる日本進出済み企業だけの一覧へ遷移する。大分類が一致していても、求人0件または`entryStatus`が`not-entered`・`pre-entry-signal`の企業を結果へ混ぜない
- 企業単位の`hiringStatus`と`salesRoles`は公開中の求人レコードから自動算出し、`積極採用`は3件以上、`採用中`は1〜2件、`継続観測`は0件とする。手入力値を表示・絞り込みの根拠にしない
- セクション説明の`（分類基準）`は画面遷移を伴わない開閉UIとし、3層の数値基準、日本未進出と求人0件を除外することを同じ画面内で明記する
- `日本未進出`と`日本進出の兆しあり`は採用温度の追加段階にせず、別軸の黄色い注目企業枠として並置する。`/companies?entry=pre-entry#company-results`は両方、`entry=not-entered`は現行シグナル未確認、`entry=pre-entry-signal`は日本法人・常設拠点が未確認で、設立予定の公式発表、日本責任者・市場担当者、現行の日本市場向け公式求人など具体的な動きを現在確認した企業だけを再現する。過去求人のみの企業は後者へ含めない。日本在住・日本担当者がいる場合を含み、法人・雇用主体とは別軸であるという定義を一覧と個別ページに表示する
- 全領域を個別カードで列挙する詳細グリッドは表示しない。求人掲載中の企業数、掲載中の営業求人数、営業求人を確認できた領域数を、最終更新日の左隣にまとめて表示する
- 現時点では募集終了履歴を含まないことを注記する
- データを水増しせず、`lib/market-data.ts`の求人と企業カテゴリだけを使用する
- `entryStatus`が`not-entered`・`pre-entry-signal`の企業は、日本進出済み企業の求人掲載中企業数・営業求人数・採用温度の集計へ含めない。`pre-entry-signal`の現行求人は個別ページでのみ応募対象として明示する
- 分類ロジック、遷移先企業、日本未進出・求人0件の除外、企業単位の採用状況自動算出は自動検証し、混入や基準の不一致がある状態で公開しない

### 5.3.1 日本未進出企業の表示

日本未進出企業の個別ページは、Gongページを起点に確定した`ops/pre-entry-company-standard.md`を正本とする。Gong固有の事実や文章は流用せず、同ファイルに定義した構造・情報密度・事実と仮説の分離を全社へ適用する。

- 企業一覧カード上部に黄色の`日本未進出`ラベルを表示し、通常の`積極採用`・`採用中`・`継続観測`バッジと混同しない
- 企業一覧には進出状況の絞り込みを設け、URLクエリ`entry=pre-entry`、`entry=not-entered`、`entry=pre-entry-signal`から直接同じ結果を再現できるようにする
- 個別ページは共通の`CompanyIntelligenceProfile`と標準セクション順を維持する。個別企業だけの独自レイアウトを作らない
- 上部の判断サマリーは「応募できるか」ではなく、日本未進出の事実、海外成長、APAC展開、日本進出を支持する材料と反証を要約する
- 会社概要では、日本進出済み企業は日本語の公式トップページ、日本未進出企業は本国の公式トップページへ遷移できる導線を置く。製品ページや採用ページを公式トップページの代替にしない
- 会社概要のグローバル経営責任者と日本法人・日本責任者は、LinkedIn人物プロフィールまたは人物検索を第一導線とする。公式プロフィール・就任発表等の公開情報はその下に1件まで表示し、氏名未確認の場合も役職を用いたLinkedIn検索導線を残す
- 日本進出の有無を問わず、会社全体のグローバル社員数を会社概要に表示する。公式の厳密値がない場合はLinkedIn企業ページ等の公開会社規模レンジを使い、厳密な在籍人数ではないことと出典を明示する。「非公開」だけで終えない
- 日本の求人が0件であることを明示し、海外報酬・Quotaを将来の日本条件として流用しない
- 未進出企業の該当見出しは`日本進出の可能性`とし、海外実績・注力エリア・APAC基盤・日本市場との親和性、進出ハードル、進出が現実的になる条件、今後見るべきシグナルを、公開事実とGenba仮説に分けて読み応えのある形で掲載する
- LinkedIn導線は日本在籍者検索ではなく、APAC・海外GTM人材の公開プロフィール検索とする。本文は個人紹介ではなく対象地域・役割・サンプル数を示した集計だけを掲載する

### 5.3.2 企業一覧カードと本社所在地

- 企業一覧カードの説明は求人状況の説明にせず、「どういう課題を、どういうテクノロジーで解決し、競合・内製・現状維持と比べてどこに優位性があるか」が企業名を知らないAEにも分かる短い価値説明とする
- `課題「...」`、`主力製品は...`のような項目ラベルを並べず、`〇〇という課題を、〇〇テクノロジーで解決し、〇〇できる点で競合と差別化する企業。`を基本構文とする。一文を述語まで完結させ、省略記号や表示途中の切断を使わない
- 説明は`CompanyPublicIntelligence.solutions`の主力製品価値を正本に、一覧用の簡潔な文章へ変換する。求人、採用、募集ポジションを説明文へ混ぜない
- デスクトップ・スマホの両方で価値説明を表示する。スマホは2列を維持し、文字サイズ、行数、カード高を調整して、企業名・価値説明・求人件数・更新日を同時に読めるようにする
- 企業一覧には`本社所在地`の絞り込みを設ける。主たる本社所在地を`米国`、`欧州`、`カナダ`、`アジア太平洋`、`イスラエル`へ正規化し、URLクエリ`hq`から同じ結果を再現できるようにする
- 本社所在地を選択した場合は、選択地域に該当する企業だけを表示し、同じ地域内では保存済みの本社所在地、企業名の順で並べる
- 全掲載企業に価値説明と本社地域が存在すること、価値説明に求人・採用文言が入っていないこと、スマホで説明を非表示にするCSSがないことを自動検証する
- 黄色は未進出状態の識別に限定し、企業評価、進出確率、推奨順位を表す色として使わない

## 6. 企業一覧仕様

### フィルター

- ソリューション領域

- 営業求人あり
- AE／SDR／BDR／Manager／Partner Sales／SE／CS
- SMB／Commercial／Enterprise
- 日本法人あり
- 日本語サイトあり
- リモート可
- 年収記載あり
- 新規参入・採用拡大中

### ソート

- `最終更新が新しい順`を初期値とし、企業調査の`lastChecked`が新しい企業を優先する
- `新着求人が新しい順`は、現在掲載中の求人レコードの`firstSeen`が最も新しい企業を優先する。求人0件の企業は後段に置く
- `求人が多い順`は、現在掲載中の確認済み求人件数が多い企業を優先する
- `企業名 A–Z`は、大文字・小文字を区別せず英字順に並べる
- `日本進出が早い順` / `日本進出が遅い順`は、公開根拠のある日本市場の進出・参入・拠点開設マイルストーンの最初の年を使う。該当マイルストーンがない場合は日本法人設立年を使う
- `日本法人での想定従業員数が多い順` / `日本法人での想定従業員数が少ない順`は、gBizINFOの事業所情報を基にした値を使う。日本未進出企業は0人とし、事業所欄に掲載がない企業・対象法人を特定できない企業は未確認値とする
- `日本法人設立が早い順` / `日本法人設立が遅い順`は、確認済みの日本法人設立年を使う
- 進出年・法人設立年・日本法人での想定従業員数の未確認値は、昇順・降順のどちらでも確認済み企業の後に置く
- 並び順はURLクエリ`sort`へ保存し、検索・各フィルターと併用して同じ結果を再現できるようにする
- 根拠のない独自スコアによる`おすすめ順`は設けない。採用シグナル順は比較可能な変更履歴データが整うまで公開しない

### 企業カード

- ロゴ（利用可能な場合）
- 企業名
- カテゴリ
- 日本市場フェーズ
- 営業求人数と前週差

## 7. 企業詳細仕様

企業詳細は単なる会社概要ではなく、読者が「今この会社を見る価値があるか」「どの求人が自分の経験に近いか」「どの会社と併願比較すべきか」を判断するための`応募判断OS`として設計する。

### 7.0 ページ改善要請

- 全企業詳細に`このページを改善`を常設し、画面遷移なしで「情報不足」「説明不明」「誤り・古さ」「UI」等の要請を送れるようにする
- 会社名、ページURL、要請種別は自動的に付け、対象箇所は任意、改善内容は必須とする
- 氏名・メールアドレスは求めず、個人情報・非公開情報を入力しないよう明記する
- Cloudflare Workerが同一origin、入力長、企業slugを検証し、honeypotとrate limitの後、件名`改善要請`で`js@genbajapan.com`へ送信する
- 送信成功・失敗・回数制限は同じdialog内で表示し、入力後に画面遷移させない

セクション順、見出し、開閉状態、必須データ、出典、移行ゲートの唯一の正本は`ops/company-page-standard.md`とする。本章は背景要件を補足し、矛盾する場合は同標準を優先する。

### セールス視点サマリー

- 見出しは「セールス観点から見たこの会社(FABE分析ベース)」とする。`FABE分析ベース`はクリックで開閉し、Feature、Advantage、Benefit、Evidenceの定義と、GenbaではCompetitorも併記する理由を同じ画面内で説明する
- ファーストビューでは、対象顧客、具体的な課題3点、主力製品の機能、競合優位性、顧客メリットを4文で常時表示する。会社名から書き始めず、AEが顧客・課題・製品・選定理由を短時間で把握できる順序にする
- 公開根拠、導入前後で測る成果指標、日本市場の需要・実績・未公開情報は`導入実績・成果指標・日本市場の見立てを見る`からクリック展開する。開いた状態では見出しを`閉じる`へ切り替える
- この2層表示を全企業と今後の新規企業の標準とし、個別企業だけの例外UIにしない
- 対象領域を明示する方が理解しやすい企業では、共通の`salesFabeOverview`を使う。対象領域と短い課題説明は常時表示し、FABE・Competitorは日本市場の見立ての直下にある`FABE分析と競合比較`から開閉表示する。データ型、列順、レスポンシブ表示は共通コンポーネントとし、企業固有のUIは作らない
- 根拠は企業公式の導入事例・製品ページ・法定開示を優先する。製品単位の導入社数、継続率、成果数値が未公開な場合は、会社全体の数値を流用せず未公開と明記する
- `です・ます`調を使わず断定調に統一し、求人タイトルの列挙や汎用的なSaaS紹介文で代替しない
- 公開情報とGenba仮説を混同せず、各社の`solutions`、`customerProof`、`sellingPlaybook`、`salesAppeal`と整合させる

### ソリューション詳細のFABE表示

- 全企業の各ソリューションは、クリック後に`機能`、`優位性`、`提供価値`、`根拠`、`競合・代替手段`の固定順で表示する
- `Feature`は製品の技術・機能・仕組み、`Advantage`は競合・内製・現状維持との相対比較、`Benefit`はBuyerの業務・財務・リスクの改善、`Evidence`はその説明を支える公開根拠と未公開情報の限界、`Competitor`は主な代替手段と実商談での比較軸を記載する
- 機能とメリットを同じ文章で済ませず、優位性は製品固有の設計・統合・運用・データ・エコシステムなどの比較可能な軸で説明する

### 応募判断サマリー

- 最上部に`今、見る価値が高い`、`条件が合えば有力候補`、`今はウォッチ候補`のいずれかを表示する
- 上記は企業の優劣、応募推奨、合格確率ではなく、確認中の求人件数と採用状況に基づく閲覧優先度とする
- 判定理由、確認中の営業求人数、採用シグナル数、最終更新日を併記する
- 向いている経験は、確認済み求人のセグメントと企業タグから一般的な近さとして示す
- 応募・合否実績と公開済み算出方法がない状態で、合格確率を数値表示しない

### 応募判断材料の充足度

- 採用状況、営業求人、ソリューション領域、日本拠点、OTE・Pay Mix、日本組織規模、Quota達成率、在籍・昇進データを主要8項目とする
- 確認できた項目だけをカウントし、未確認項目は空欄ではなく`未確認`と表示する
- 充足度は会社の評価点ではないことを画面上で明記する
- 各数字に対象地域、対象職種、期間、出典、最終更新日、サンプル数を持たせる

### 売上・従業員規模の比較

- 全企業の会社概要に`近しい規模感の外資IT企業`をクリック開閉できる共通ボックスとして表示する
- 売上とグローバル従業員数を分け、それぞれ既存掲載企業から規模の近い企業を複数社表示し、各企業ページへ遷移できるようにする
- 売上の近さは通期開示を優先し、四半期値は年率換算して判定する。ただし比較カード上では元の開示期間と数値をそのまま表示し、企業価値・成長性の優劣を示す比較ではないことを明記する
- 読者が物差しにしやすい認知度の高い外資IT企業を優先する。比較対象がない場合や売上・従業員数が非公開の場合は推測せず、その旨を表示する
- 米ドル金額は全企業ページで円換算を併記する。換算レートは`1ドル=157円`を共通基準とし、概算であることを表示する
- 個別企業固有の比較UI・比較基準を作らず、新規企業にも同じ共通処理を適用する

### 公開情報インテリジェンスとGenba仮説

情報が未開示であることだけを並べず、読者が応募仮説を立てられるよう、公開情報を次の2層で表示する。

1. `公開事実`: 企業公式、法定開示、公式求人、公式導入事例などから直接確認できる内容
2. `Genba仮説`: 複数の公開事実と外部集計を横断して導く、検証可能な編集上の読み解き

各Genba仮説には必ず以下を持たせる。

- 仮説の結論と確度（高・中・探索中）
- 仮説を支持する材料
- 仮説が外れる可能性を示す反証・留保
- 面接で検証できる具体的な質問
- 根拠URL、情報種別、対象地域・職種、最終確認日

企業公式、法定開示、外部集計、コミュニティ情報はラベルで分ける。グローバルの自己申告データを日本法人の事実として扱わず、コミュニティ情報だけを根拠に断定しない。OTE、Pay Mix、Quota達成率など非公開の数値は作らず、方向性の仮説と確認方法を示す。

スポンサー企業から提供された一次情報は`企業提供事実`として表示し、Genba仮説と分離する。対価により仮説の結論や併願順位を変更せず、提供事実によって仮説が変わる場合は更新理由と更新日を残す。

### ソリューション・ポジション・組織

- ソリューション領域、主なBuyer、解決課題、営業として得られる経験、面接で確認すべき論点を表示する
- ソリューションの強さは、国内導入事例、競合差別化、顧客継続・拡張などの証拠単位で示し、総合点だけで断定しない
- 求人ごとに勤務地、言語、セグメント、初回確認日、最終更新日を表示する
- OTE、Pay Mix、新規／既存比率、Quotaは公式情報等で確認できた場合だけ掲載する
- 日本社員数、AE人数、平均在籍年数、入社元、転職先は集計値とし、個人名一覧や人物評を作らない
- 日本責任者・営業リーダーは公式プロフィール、就任リリース、公開インタビューのみを参照する

### 併願候補

- 同じソリューションクラスター、Buyer、求人セグメント、企業タグの近さから最大3社を表示する
- `Genba分析`と明記し、競合関係や個人の合格可能性を断定しない
- スポンサー契約によって候補順位や分析理由を変更しない

### 出典台帳

- 企業公式、法定開示、外部集計、コミュニティ情報をラベルで区別する
- ページ上の最終更新日と、内部データの最終確認日を区別して保持する

## 10. 収集・更新フロー

### 情報源の優先順位

1. 企業公式Career・ATS・ニュースルーム・日本サイト
2. 信頼できる求人・報道媒体
3. X・LinkedIn・読者提供情報

### 日次処理

1. 登録済み企業の公式URLを巡回
2. 公開中求人を抽出
3. 前回スナップショットと比較
4. 追加・削除・変更候補を生成
5. 関連ニュースを照合
6. AIが職種、セグメント、信頼度を分類
7. 出典・取得日・差分を保存
8. デイリーブリーフ、X原稿、ニュースレター候補を生成
9. ガードレールとリンク切れを検査
10. 承認後に公開・デプロイ

### 収集上の制約

- robots.txt、利用規約、アクセス頻度を尊重する
- ログインや回避技術が必要な取得は行わない
- 求人媒体を公式Careerの代替ソースとして無断複製しない
- 取得できない情報を推測で埋めない
- 自動収集が許されないサイトは手動確認または公式フィードを利用する

## 14. スポンサー・求人掲載

### `/advertise`

- 最も価値が出る3つの顧客像と、それぞれが抱える採用課題
- 初期3社限定、まず1カ月80,000円（税別）で開始でき、効果測定には3カ月の継続を推奨する実証パートナー商品
- `Sponsored`企業ページ、`企業提供事実`、ニュースレター月2回、`PR`表記付きX配信月1回、公式求人への計測リンク、月次レポート、月1回までの更新
- 初月80,000円と推奨3カ月総額240,000円、月ごとの配信回数、計測指標を使った費用対効果の判断材料
- 成果を保証せず、自社の既存採用チャネルと比較できるCPA、面接単価、採用単価の算式とレポート例
- Sponsored表記方針
- 審査基準
- 掲載レポート例
- 問い合わせフォーム
- 日本語版から英語版`/en/advertise`へ切り替えられ、英語版から日本語版へ戻れること

MVPでは自動決済を実装せず、掲載審査後に請求する。無審査セルフサーブ掲載は、信用と法務対応が整ってから検討する。

- `company_filter_used`
- `job_view`
- `official_apply_click`
- `sponsor_click`
- `advertise_inquiry`
