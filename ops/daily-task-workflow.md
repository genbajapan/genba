# デイリータスク・ワークフロー

最終更新: 2026-08-12

「デイリータスク」という指示を受けた場合に実行する、拡張版の運用ワークフロー。`ops/daily-workflow.md`(日々の求人差分更新)とは別に、企業追加・全社更新・X下書き・SEO/AEO点検をまとめて実行する回として使う。

このファイルへ事業ルールを複製しない。矛盾する場合は`PROJECT_RULES.md`および`docs/09-pivot-business-plan.md`を優先する。

## 0. 開始確認

`ops/daily-workflow.md`の0章と同様に、`PROJECT_RULES.md`・`ops/job-publication-and-sponsor-policy.md`・`ops/guardrails.md`を読み、`git status --short`で他の作業と競合しないか確認してから始める。

## 1. 新規企業を3社追加する

- 1回あたり、日本進出済みの小中規模外資を2社、日本未進出の注目外資を1社追加する(2026-08-12 Jio指示)。件数を理由に1社あたりの調査量・仮説・標準フォーマットの情報密度を下げない
- 選定基準は`docs/09-pivot-business-plan.md`5.1に従う。知名度ではなく「日本進出済みだが日本語情報が乏しい」ことを優先する
- 通常のデイリータスクでも、日本進出済み2社に加えて「日本未進出の注目企業」を1社追加する。未進出企業はGongを起点に確定した標準フォーマットで作り、現在応募できる企業・求人と同じ集計へ混ぜない
- 初期の追加分は、ある程度名前を聞いたことがある知名度の企業から始め、実施回を重ねるごとに、より知名度の低いニッチな企業へ選定範囲を広げていく(2026-08-07 Jio指示)
- 既存の登録企業とカテゴリ・業界が偏りすぎないよう配慮する
- 各社について、国内(OpenWork・OpenMoney・日本語ニュース・日本法人プレスリリース)、海外(英語ニュース・IR資料・決算資料)、LinkedIn(現従業員・カントリーマネージャー等の異動)、公式採用ページの実求人を横断して徹底的に調査する。手を抜かず、Genbaが読者に届けたい「解像度の高さ」を満たす
- 日本未進出企業を扱う場合は、`ops/pre-entry-company-standard.md`を必ず最初から最後まで読み、Gongを正準サンプルとする同一構造・同等以上の情報密度で作成する。国内情報が少ないことを理由に薄くせず、海外公式の業績・資金調達・顧客事例・製品・Trust、APACの公式拠点と求人、製品の日本語対応、海外GTM人材の公開プロフィール集計、日本進出の追い風と障壁を横断する。日本法人・日本求人・国内顧客がないこと自体も反証として保存する
- 新規企業の会社概要には、進出済みなら日本語の公式トップページ、未進出なら本国の公式トップページへの導線と、会社全体のグローバル社員数を必ず入れる。公式の厳密値がない場合はLinkedIn企業ページ等の公開会社規模レンジを出典・留保付きで表示し、「非公開」だけで規模感を欠落させない
- `lib/company-public-intelligence.ts`の`CompanyPublicIntelligence`型に沿って、既存登録企業と同じ深さで全フィールドを埋める(`salesSnapshot`、`marketStatus`、`sellingPlaybook`、`facts`、5件の`hypotheses`、`cultureNotes`、`customerProof`、`externalSignals`、`roleLens`、`leadership`、`companyStats`、`salesAppeal`、`interviewPrep`、`solutions`、`fitTags`、`comparisonMap`、`sources`)。`marketStatus`は日次の株価スナップショットではなく、変遷・成長性ストーリー形式(`growthSummary`+`milestones`、上場企業は`stockLinkUrl`)で作成する
- ページ上部の`営業視点サマリー`(`salesSnapshot`)を必ず作る。文章は原則3文とし、1文目で「誰に、何を提供する会社か」、2文目で顧客が抱える具体的な課題を3点、3文目で「どの部門・経営課題へ入り、何へ提案を広げられることが営業として面白いか」を断定調で示す。`です・ます`調、求人の列挙、どのSaaSにも当てはまる抽象表現だけで済ませない。`solutions`、`customerProof`、`sellingPlaybook`、`salesAppeal`の根拠と矛盾しないよう企業ごとに編集する
- 新規企業ページは、共通の`CompanyIntelligenceProfile`、`CompanyPublicIntelligence`型、本章に定義した件数目安、`ops/company-selling-playbook-standard.md`を参考実装とし、同じセクション順、見出し、カード構成に合わせる。Salesforce個別ページは編集対象から削除済みだが、同ページを起点に改善してきた粒度と品質基準はこの共通仕様へ引き継ぐ。固定するのはフォーマットだけであり、各カード内の根拠と分析は、企業ごとに確認できる情報を徹底調査して最善の深さにする。企業固有の表示コンポーネント、CSS、スキーマ、追加セクションは、Jioが明示的に指示した場合を除き作らない
- 標準の構造は、原則として`milestones` 5件、`growthDrivers` 3件、`riskHypotheses` 2件、日本の成長シグナル 3件、`facts` 6件、`hypotheses` 5件、`customerProof` 3件、`externalSignals` 2件、`salesAppeal` 3件、`interviewPrep` 4件を目安とする。これは調査量や文章の深さの上限ではない。`sellingPlaybook`は3つの課題レンズ、4段のストーリー(背景・課題・解決策・選定の理由)、オープニングの問いかけ、価値仮説、よくある反論への返しで構成する
- 調査は検索上位の数ページで終えず、企業公式サイト、日本法人の発表、公式求人、製品資料、国内導入事例、IR・決算資料・法定開示、公式インタビューを横断する。数値・日付・固有名詞は複数ソースで照合できる限り照合し、強い根拠と反証の両方から仮説を組み立てる
- 各仮説は、結論、支持材料、反証・留保、確度、面接で検証できる質問が一続きになるよう編集する。公開事実の要約だけで止めず、「営業候補者の応募判断にどう影響するか」まで言語化する
- 公式根拠が不足している項目は、件数を揃えるために推測・水増ししない。その場合も独自フォーマットに変えず、標準の枠内で「未確認」「非公開」「仮説」を明示する
- 日本未進出企業の進出時期・確率・最初の採用職種・報酬・Quotaを事実として書かない。`2〜3年以内`等は`Genba仮説`としてのみ扱い、支持材料、反証、確度、継続観測項目を必ずセットにする
- 日本未進出企業の`日本進出の可能性`は短い結論だけで済ませない。海外実績・現在の事業展開・注力エリア・APAC基盤・日本市場との親和性を事実として整理し、進出を後押しする材料、進出ハードル、現実化に必要な条件、継続観測シグナルを別々に書く。最低件数と公開前チェックは`ops/pre-entry-company-standard.md`に従い、事実と仮説を混ぜず、進出時期を断定しない
- 公開前に新規企業ページを`CompanyIntelligenceProfile`の全セクションと、現時点で最も情報密度の高い既存企業ページ1社以上と実画面で比較し、セクション順、見出し、カード数、文章量、展開パターンが標準内かを確認する。比較先の会社固有情報をコピーせず、独自セクションや明らかに薄い項目が残っている場合は完了・公開しない
- 各社の追加後に、現時点の最良ページと比べて「より強い出典、より鋭い仮説、より実用的な面接質問にできないか」を再点検する。共通フォーマット自体の改善案に気づいた場合は、企業固有で先行実装せず、全社共通の改善案としてJioへ提案する
- `lib/market-data.ts`に会社情報と、実在が確認できた求人だけを追加する。求人詳細が取得できない場合は無理に件数を揃えない
- 企業ごとに製品固有の詳細カテゴリ`category`と、一覧・絞り込み用の`broadCategory`を分けて設定する。`broadCategory`は`lib/solution-categories.ts`の7分類から選び、1社だけのために新しい大分類を増やさない。既存7分類では意味が大きく損なわれる場合は、全社の再分類案としてJioへ確認する
- 各求人の`careerInsights`のうち`tenureAndPromotion`・`priorCompanies`・`nextCompanies`は、「公開データがない」で思考停止しない。その会社(またはその求人と同じ職種・セグメント)についてLinkedInで公開プロフィールを複数検索し、入社元・在籍傾向・転職先の**傾向**を掴んだ上で書く。ただし`ops/job-publication-and-sponsor-policy.md`3章・`ops/guardrails.md`2章の非交渉ルールを必ず守る
  - 個人を特定できる形の経歴紹介(実名はもちろん、実名を伏せても役職・在籍期間・前職・専門性の組み合わせで一人に絞り込める記述)を作らない。書けるのは対象地域・職種・サンプル数・出典を明示した**集計・傾向**まで(例:「LinkedIn公開プロフィールを数件確認した限り、前職は◯◯系企業であるケースが多い」)
  - カントリーマネージャーや営業リーダーなど、社内に1人しかいない役職者は、集計しても実質的に個人が特定されるため対象外とする。この層に触れる場合は、公式プロフィール・就任発表・本人の公開インタビューだけを根拠にする(LinkedInの職歴を根拠にしない)
  - LinkedIn検索をしても実例・傾向が確認できない場合は、製品領域・セールスモーション・ターゲット顧客層から導ける仮説を、根拠を示した上で書く。これは手抜きではなく、個人情報を扱わないための正当な代替手段であり、そのまま採用してよい(2026-08-10、Jio指示を受けてルールを修正。当初「実例を具体的に引用する」としていたが、既存の集計値限定ルールと矛盾していたため訂正)
- 事実確認できない情報を補完・推測・創作しない

## 2. 既存企業ページを全社更新する

求人情報の鮮度をトークン消費を抑えて保つため、軽量な確認を基本にし、深掘りは必要な場合だけ行う(2026-08-08方針)。

### 2-1. 求人リンクの軽量チェック(毎回・低コスト)

- `lib/market-data.ts`の登録済み求人URLは、WebFetch(要約を伴う取得)ではなく単純なHTTPステータス確認(200か404/リダイレクトか)だけで生死を確認する
- ATSの公開JSON APIが判明している企業は、それを直接叩いて現在の求人一覧(タイトル・URL・掲載日)を取得し、保存データと突き合わせる。WebFetchより大幅に低コストで新着・終了を検出できる
  - Greenhouse: `https://boards-api.greenhouse.io/v1/boards/<board-token>/jobs`
  - Workday: `https://<company>.wd#.myworkdayjobs.com/wday/cxs/<company>/<board>/jobs`(POSTで`searchText`指定可、`curl`で直接叩ける)
- 404・リンク切れが確認できた求人は募集終了として取り下げる。`hiringStatus`・`salesRoles`は公開中の求人レコードから自動算出し、3件以上を`積極採用`、1〜2件を`採用中`、0件を`継続観測`とするため、手入力値を表示の根拠にしない
- ソリューション領域の採用温度は`docs/10-website-renewal-spec.md`の固定基準に従う。日本未進出企業と求人0件の企業を`HOT`・`Active`・`Selective`の集計・遷移先へ含めない
- API・ステータス確認で新しいタイトルが見つかった場合は、その求人に限り通常と同じ深さ(`descriptionSummary`・`genbaTake`・`compensationReality`・`desiredProfile`・`careerInsights`)の分析を書く。発見コストが下がっても、書く内容の深さは省略しない
- ボット対策等でAPI・ステータス確認ができない企業は、この軽量チェックでは新着求人を検出できない前提を置き、2-2で補う

### 2-2. 全社の深掘り棚卸し(週1回程度、または軽量チェックで不審な変化を検知した場合)

- 軽量チェックでカバーできない企業を中心に、WebSearch/WebFetchで通常の棚卸しを行う
- 求人タイトルは同じでも中身(セグメント・要件)だけが変わったケースは軽量チェックでは検知できないため、ここで確認する

### 2-3. marketStatus(上場企業)

- 日次の株価・時価総額・アナリスト評価の再取得は行わない(2026-08、`marketStatus`を変遷・成長性ストーリー形式へ変更済みのため)
- 買収・上場廃止・大型ニュースなど、`milestones`に追加すべき重大な出来事がないかだけ確認する。なければ`researchedAt`の更新のみでよい

### 2-4. marketStatus(非上場企業)

- IPO見通し・オーナーシップ状況に変化がないか確認する

いずれも、変更がない項目は`researchedAt`等の確認日だけ更新し、内容を書き換えない。

## 4. SEO/AEOの最適化状況を点検する

最新ベストプラクティスの再調査(WebSearch等)は週1回を目安とし、それ以外の回は固定チェックリストだけで済ませる(2026-08-10、毎回リサーチし直すのはトークン消費に見合わないとJioが判断)。

- 本ファイル末尾「状態トラッキング」の`直近の本格SEO/AEOリサーチ日`を確認する
- 前回の本格リサーチから7日以上経過している場合、または記録がない場合は「本格チェック」を行う
- 7日未満の場合は「簡易チェック」のみ行う

**本格チェック(週1回目安)**

- 実行時点の最新のSEO・AEOベストプラクティスを調べる。ルールは時間とともに変わるため、固定チェックリストだけに頼らない
- 下記「簡易チェック」の項目に加え、新しく出てきた観点(構造化データの新形式、AI回答エンジン側の引用傾向の変化など)がないか確認する
- 完了したら、本ファイル末尾の状態トラッキングの日付を実行日に更新する

**簡易チェック(それ以外の回)**

- 新しいベストプラクティスの再調査は行わず、以下の固定項目だけを現在のサイト状態と照合する
  - 各ページのtitle・meta description・canonical・OGP・構造化データ(JSON-LD)
  - `/llms.txt`(`app/llms.txt/route.ts`で動的生成)・`/robots.txt`・`/sitemap.xml`が最新のページ構成を反映しているか
  - 見出し構造(h1/h2)や、AI回答エンジンに引用されやすいQ&A形式のコンテンツ設計
  - 併願候補・比較表など内部リンクの機能状況
  - 画像のalt属性、明らかな表示速度の問題

最適化できていない箇所は、本格・簡易いずれの回でも修正する。サイト構造の大きな変更が必要な場合は、実施前にJioへ報告してから進める。

## 5. 月曜日・木曜日・土曜日はニュースレター下書きを作成する

「デイリータスク」の実行日が日本時間の月曜日・木曜日・土曜日に当たる場合は、1〜4章の結果を使って、その日のGenbaニュースレター下書きまで作成する。火曜日・水曜日・金曜日・日曜日はこの章を省略する。

- `ops/daily-workflow.md`4章のニュースレター候補を、読者へそのまま送れる原稿へ仕上げる
- 新着・終了求人の差分、注目の進出済み企業1社、注目の未進出外資1社、外資AE向け海外一次情報の要点を基本構成とする。未進出企業は現在応募できる会社と誤認させず、進出可能性・追い風・障壁・継続観測点を短く分離する。ただし、確認できる重要な変化がない項目を件数合わせで作らない
- 件名、プレヘッダー、本文、CTA、参照した公式URL、確認日を含める
- 本文の書き出しは`Genba編集長です。`とする
- 1段落を短くし、話題・事実・`Genba分析`・CTAの間に十分な改行を置く。長文を詰め込まず、スマートフォンでも読者が流れを追える構成にする
- 本文中へURLをそのまま表示しない。`公式求人を見る`、`企業ページを見る`など、遷移先が分かる文字列へリンクを埋め込む
- 事実と`Genba分析`を分離し、数字・日付・企業名・求人リンクを送信前チェックできる状態にする
- 下書きは`content/newsletter/drafts/YYYY-MM-DD.md`へ保存する
- Kitへの入稿・予約設定・テスト送信・本配信は行わず、Jioへ下書きと確認事項を提示して明示承認を待つ
- Jioがその回に「配信して」などメール送信を明示承認した場合だけ、最終確認後にKitで予約または配信する

## 6. 検証・報告

- `npm run check`を実行する
- 追加した企業、更新した企業ページ、作成したX下書き、SEO/AEOの修正内容(本格/簡易のどちらを行ったか含む)を簡潔に報告する
- 月曜日・木曜日・土曜日は、ニュースレター下書きの保存先、件名、主要トピック、送信前の確認事項も報告する
- 対話セッションでは、`npm run check`成功後に対象ファイルだけを明示してpush・本番公開し、主要URLを確認する。実行ごとの確認は求めない。スケジュール実行は`PROJECT_RULES.md`7章と`ops/daily-workflow.md`7-1に従う
