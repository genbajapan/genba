# デイリータスク・ワークフロー

最終更新: 2026-08-23

「デイリータスク」という指示を受けた場合に実行する、拡張版の運用ワークフロー。`ops/daily-workflow.md`(日々の求人差分更新)とは別に、企業追加・全社更新・X下書き・SEO/AEO点検をまとめて実行する回として使う。

このファイルへ事業ルールを複製しない。矛盾する場合は`PROJECT_RULES.md`および`docs/09-pivot-business-plan.md`を優先する。

`ops/daily-workflow.md`の0章と同様に、`PROJECT_RULES.md`・`ops/job-publication-and-sponsor-policy.md`・`ops/guardrails.md`を読み、`git status --short`で他の作業と競合しないか確認してから始める。

## 2. 既存企業ページを全社更新する

求人情報の鮮度をトークン消費を抑えて保つため、軽量な確認を基本にし、深掘りは必要な場合だけ行う(2026-08-08方針)。

### 2-1. 求人リンクの軽量チェック(毎回・低コスト)

- `lib/market-data.ts`の登録済み求人URLは、WebFetch(要約を伴う取得)ではなく単純なHTTPステータス確認(200か404/リダイレクトか)だけで生死を確認する
- ATSの公開JSON APIが判明している企業は、それを直接叩いて現在の求人一覧(タイトル・URL・掲載日)を取得し、保存データと突き合わせる。WebFetchより大幅に低コストで新着・終了を検出できる
  - Greenhouse: `https://boards-api.greenhouse.io/v1/boards/<board-token>/jobs`
  - Workday: `https://<company>.wd#.myworkdayjobs.com/wday/cxs/<company>/<board>/jobs`(POSTで`searchText`指定可、`curl`で直接叩ける)
- 404・リンク切れが確認できた求人は募集終了として取り下げる。`hiringStatus`・`salesRoles`は公開中の求人レコードから自動算出し、3件以上を`積極採用`、1〜2件を`採用中`、0件を`継続観測`とするため、手入力値を表示の根拠にしない
- ソリューション領域の採用温度は`docs/10-website-renewal-spec.md`の固定基準に従う。日本未進出企業と求人0件の企業を`HOT`・`Active`・`Selective`の集計・遷移先へ含めない
- API・ステータス確認で新しいタイトルが見つかった場合は、その求人に限り通常と同じ深さ(`descriptionSummary`・`genbaTake`・`compensationReality`・`desiredProfile`・`careerInsights`)の分析を書く。発見コストが下がっても、書く内容の深さは省略しない
- ボット対策等でAPI・ステータス確認ができない企業は、この軽量チェックでは新着求人を検出できない前提を置き、2-2で補う

### 2-2. 全社の深掘り棚卸し(週1回程度、または軽量チェックで不審な変化を検知した場合)

- 軽量チェックでカバーできない企業を中心に、WebSearch/WebFetchで通常の棚卸しを行う
- 求人タイトルは同じでも中身(セグメント・要件)だけが変わったケースは軽量チェックでは検知できないため、ここで確認する

### 2-3. marketStatus(上場企業)

- 日次の株価・時価総額・アナリスト評価の再取得は行わない(2026-08、`marketStatus`を変遷・成長性ストーリー形式へ変更済みのため)
- 買収・上場廃止・大型ニュースなど、`milestones`に追加すべき重大な出来事がないかだけ確認する。なければ`researchedAt`の更新のみでよい

### 2-4. marketStatus(非上場企業)

- IPO見通し・オーナーシップ状況に変化がないか確認する

いずれも、変更がない項目は`researchedAt`等の確認日だけ更新し、内容を書き換えない。

## 3. X下書きを作成する

- `ops/x-content-strategy.md`を正本とし、Harvey・Dropbox見本の骨格による`1社深掘り`以外の企画を作らない
- 各X本文は、公式に確認した創業地を日本語で表す`〇〇発`から必ず書き始める。現在の本社所在地や登記国から創業地を推測せず、使用した国・地域表記と根拠を事実確認メモへ残す
- 毎回、Genba掲載企業全体から異なる2社を選び、`1社深掘り`を1本ずつ、合計2本作る。新規追加企業、当日の更新企業、直近7日以内に動いた企業を優先する必要はない
- 対象候補は本番のGenba企業一覧と企業ページで現在掲載中であることを確認し、内部データや過去ページの履歴だけが残る非公開・削除済み企業を除外する。そのうえで直近の下書き・投稿履歴との重複を除いて広く選ぶ。創業ストーリー、創業者の原体験、製品誕生のきっかけ、企業名の由来等を公式情報または信頼できる公開インタビューで確認できない候補は、一般的な市場説明で代用せず別企業へ切り替える
- `1社深掘り`は、その会社を今回取り上げる理由と会社固有の面白い始まりから入り、現在の事業、現在の規模感、なぜ伸びているか、具体的な導入事例、現行求人へつなぐ。規模感は必ず読者が知る2社と比較し、指標・時点・定義の違いを明記する。成長理由は`Genba分析では`という定型句を使わず、顧客の困りごと、導入理由、利用・契約が広がる理由を誰にでも分かる因果で書く。外資IT読者が抱くもっともな反論や競争リスクがある場合は先回りして示し、部分的に認めたうえで会社固有の勝ち筋を説明する。売上、ARR、顧客数、社員数、評価額等の定義を混同しない
- 日本進出済み・未進出は同じ`1社深掘り`で扱い、日本法人、拠点、日本向け求人、国内顧客事例の確認状況を明記する
- `取り上げる理由 → 面白い始まり → 現在の事業 → 現在の規模感 → なぜ伸びているか・勝ち筋 → 具体的な導入事例 → 現行求人 → 企業ページCTA → メルマガ固定CTA`の順で書く。会社説明や求人列挙から始めない。導入事例は公式の日本企業事例を優先し、確認できない場合だけ海外事例を使う。求人は`今日時点での日本向け公式求人はN件。`から始める。5件以下を目安にポジション名を列挙し、件数が多い場合は長い列挙を避け、Genbaで対象ロールの情報を確認し公式求人へ進める旨を書く。公式件数から採用の勢いを読む場合は、断定せず短い一人称の所感または`感じられます`等の留保付き表現にする。役割の詳細、応募条件、仕事の学びへは広げない
- 該当企業ページへの最終UTM付きURLを入れ、公式出典、確認日、留保を`事実確認メモ`へ残す
- 企業ページCTAの後に空行を入れ、`ops/x-content-strategy.md`所定のメルマガ固定CTAを文面・改行・URLとも改変せず、投稿本文の最後へ付ける。既存の企業ページ用UTMとは別の固定計測リンクとして扱う
- 直近の下書き・投稿履歴と同じ企業、創業話、学びを繰り返さない
- 本文と事実確認メモを`content/x/drafts/`へ保存する
- 転職Tips、営業の学び、引用post案、Genba単独告知、スレッド、比較企画を作らない。過去案も再利用しない

## 5. 月曜日・木曜日・土曜日はニュースレター下書きを作成する

「デイリータスク」の実行日が日本時間の月曜日・木曜日・土曜日に当たる場合は、1〜4章の結果を使って、その日のGenbaニュースレター下書きまで作成する。火曜日・水曜日・金曜日・日曜日はこの章を省略する。

- 配信時刻は曜日を問わず同日19:30（Asia/Tokyo）に固定する。Jioがその回に配信または予約を明示承認した場合も、別時刻を指定されない限り19:30へ設定する
- `ops/daily-workflow.md`4章のニュースレター候補を、読者へそのまま送れる原稿へ仕上げる
- シリーズ名は`Genba発掘`とし、本文見出しを`Genba発掘 #NNN`の連番にする。過去の下書き・配信記録を確認し、番号を重複させない
- ニュースレターは企業を深掘りし切る場ではなく、毎回新しい企業を発見する入口とする。1通につき5社を短いカード形式で紹介し、詳しい事実・仮説・反証・面接質問は各企業ページへつなぐ
- 5社は原則として異なるソリューション領域から選び、現在応募可能な公式求人を確認できる企業を3社以上、認知度の高いアンカー企業を1社以下、日本未進出企業を1社以下とする
- 通常の編集選定では、直近45日以内にニュースレターで紹介した企業を原則再掲載しない。重要な求人・組織変更が確認できた場合は、変更点を明示したうえで例外にできる
- 各社のカードは、`会社名・領域・状態ラベル`に続く2段落とCTAの固定構成とする。第1段落は`何を解決する会社か → その会社固有の面白さ → 今回公式確認した求人・採用・日本進出の動き`の順で書く。会社説明は省略せず、一般的な市場説明で水増しせず、公式に確認できる製品の成り立ち、顧客成果、事業規模、独自のGTM、市場の難しさから他社と区別できる特徴を1つ選ぶ。判断に有用な実績・数字は最も強い1つを優先する
- 第2段落は太字の`仕事として見ると：`から始め、`誰のどんな課題を扱う役割か → 商談や責任をどこまで広げられるか → 何を経験できるか → 応募前に確認すべき重要な未公開・未確認項目`の順で書く。事実にない魅力、合格可能性、将来性を補完しない。未確認点は読者の判断に重要な2〜4項目へ絞る
- 求人の公開日や前回からの差分を確認できない場合は`新着`、`採用開始`と断定せず、`今回、公式求人を確認`と記す。新着・再掲載・増加・終了は、前回の確認記録と現在の公式情報を比較できる場合だけ使う
- CTAは`論点を見る`、`構造を見る`などの抽象表現だけで終わらせず、求人・役割・日本組織・応募前の確認点から遷移先で得られる答えを具体的に示す。日本未進出企業だけは`仕事として見ると：`を`日本進出を先回りすると：`へ置き換え、現在応募できないこと、進出の成立条件、次に追うシグナルを明示し、CTAは進出の兆し・成立条件・未確認点を示す
- 1社は2つの短い段落、20〜28秒程度で判断できる長さを目安とする。英語は公式の固有名詞・役職名・意味を保つのに必要な用語に絞り、日本語で意味が変わらない説明は日本語にする。本文全体は読了3分を上限とし、5社すべてを調べることを求めず、1社でも気になる会社が見つかる設計にする
- Kitでは`docs/11-newsletter-kit-setup.md`の「各社カードの入稿テンプレート」と`Genba発掘`共通デザインを使う。濃紺ヘッダーに号数と読了時間を表示し、5社を番号付きカードと薄い区切りで見せ、状態識別に必要な色だけを使う。各社CTAはテキストリンク、メール全体の最後のCTAだけを濃紺ボタンにする
- 新着・終了求人、採用変化、日本進出シグナル、海外一次情報は5社を選ぶ根拠として使う。確認できる重要な変化がない項目を件数合わせで作らない
- 日本未進出企業は現在応募できる会社と誤認させず、進出可能性・追い風・障壁・継続観測点を短く分離する
- スポンサー企業は5社中最大1社とし、原則として3番目のカードへ`広告｜SPONSORED DISCOVERY`と表示する。メール冒頭にも広告枠を含むことを明示し、企業提供事実とGenba独立分析を分ける
- 契約上の月2回のスポンサー掲載は45日以内の再掲載制限の例外にできる。ただし、再掲載は有料の掲載機会であることを隠さず、評価・順位・推薦表現を有利に変えない
- 件名、プレヘッダー、本文、CTA、参照した公式URL、確認日を含める
- 本文の書き出しは`Genba編集長です！`、続けて`皆さん、いつもありがとうございます。`とする
- 1段落を短くし、話題・事実・`Genba分析`・CTAの間に十分な改行を置く。長文を詰め込まず、スマートフォンでも読者が流れを追える構成にする
- 本文中へURLをそのまま表示しない。`3つのAE求人とOTEを比較する`、`日本組織と求人の実態を見る`など、遷移先で得られる答えが分かる文字列へリンクを埋め込む
- Genba内の各社CTAには`utm_source=newsletter&utm_medium=email&utm_campaign=genba_hakkutsu_<号数3桁>&utm_content=company_<掲載順2桁>_<企業slug>`を必ず付ける。末尾CTAは遷移先に応じて`footer_companies`、`footer_jobs`、`footer_preentry`を使う。既存queryとfragmentを壊さず、配信前のテストメールで実URLを確認する
- メール最下部へ`docs/11-newsletter-kit-setup.md`所定のスポンサー相談導線を置き、号数に対応するUTMを付ける。通常コンテンツより目立たせず、スポンサー掲載がない号でも相談窓口として表示する
- 事実と`Genba分析`を分離し、数字・日付・企業名・求人リンクを送信前チェックできる状態にする
- 下書きは`content/newsletter/drafts/YYYY-MM-DD.md`へ保存する
- Kitへの入稿・予約設定・テスト送信・本配信は行わず、Jioへ下書きと確認事項を提示して明示承認を待つ
- Jioがその回に「配信して」などメール送信を明示承認した場合だけ、最終確認後にKitで予約または配信する
- 明示承認後も、予約・本配信の前にKitから毎号テスト送信する。本文のデスクトップ・スマートフォン表示、5社と末尾のCTA、実際の遷移先とUTM、配信停止導線、送信元、件名、プレヘッダーを確認し、下書きに`testedAt`を記録する。テスト未実施または不合格の号は、予約・本配信しない
- 19:30を過ぎた場合は、明示承認なく即時配信や別時刻への変更を行わない。下書きを保持し、Jioへ次回の扱いを確認する
