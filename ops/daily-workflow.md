# Genba日次運用・共有ワークフロー

このワークフローはCodexとClaude Codeで共用する。ツール固有のコマンドやスキルへ内容を複製しない。

## 0. 開始確認

1. `PROJECT_RULES.md`を読む
2. `ops/job-publication-and-sponsor-policy.md`と`ops/guardrails.md`を読む
3. `git status --short`で他の作業を確認する
4. `lib/market-data.ts`、直近の公開記事、X下書き、更新日を確認する
5. 他方のエージェントによる未完了変更と競合する場合は上書きせず停止する

## 1. 公式情報を調査する

### 企業のTier分けと調査頻度

登録企業は、知名度ではなく「情報の非対称性」（Genba以外でどれだけ情報が出ているか）を基準にTierを分ける。

- Tier1: 日本進出したばかりの小規模〜中堅外資、または大手の陰で情報が少ない外資。毎日〜週複数回確認し、企業タイムライン・Genba分析を厚く作る
- Tier2: 上記以外の追跡企業。週1〜2回程度の確認で基本情報の鮮度を保てば十分とする

大手・有名企業であることだけを理由にTier1へ格上げしない。他媒体で既に十分報じられている企業は、基本情報の鮮度維持を優先し、深掘りの優先順位は下げる。

登録企業の公式Career、公式ATS、公式ニュースルーム、日本公式サイトを確認する。

公開対象が300社へ到達した後は、`ops/genba-300-selection-standard.md`に従って、日次の採用・残留・除外レビューを行う。全社の主要URLを毎日確認し、前日から動いた企業を再採点する。加えて300社を7群に分けて毎日約43社を深く確認し、全社を7日以内に一巡する。新規候補と既存企業を同じ100点基準で比較し、追加候補上位3社、除外候補上位3社、入れ替えペア、点差、根拠、反証、確信度を作る。変化がなければ候補を捏造せず`入れ替えなし`と報告する。

公開対象が初めて300社へ到達した実行では、同じデイリータスク内で初回判定まで続ける。判定条件を満たす入れ替えは最大3組まで一対一で自動実行し、Jioの追加指示を待たない。日次確認完了後は、追加・入れ替えの有無にかかわらず、`js@genbajapan.com`へ結果をKitのテスト送信で通知する。掲載変更がない日は`変更なし`、確認を完了できなかった日は送信可能なら`確認未完了`とする。

Adyenおよび決済受入、acquiring、processing、payment orchestration、資金移動、Merchant of Recordを主要商材または主要GTMにする企業は調査・追加候補から除外する。決済機能を一部に持つ隣接企業は主要商材かを確認し、曖昧なら公開候補に入れずJioへ確認する。

- 新規求人
- 募集終了
- 職種名、勤務地、担当領域、要件の変更
- 日本組織の採用拡大を示す公式ニュース

求人媒体・SNS・検索結果は発見目的に限り、公開根拠は公式ページで確認する。ログイン、制限回避、過剰アクセスを行わない。

## 2. 差分候補を作る

前回データと比較し、追加・変更・終了候補を作る。各候補に以下を含める。

- 企業名
- 求人タイトル
- 変更種別
- 公式URL
- 初回確認日
- 最終確認日
- 公式確認できる事実
- `Genba分析`がある場合は事実と分離した説明
- 確信できない点と公開リスク

推測で空欄を埋めない。求人票の本文を大量にコピーしない。

企業詳細の公開情報インテリジェンスを更新する場合は、公式決算・法定開示・日本向け求人・国内導入事例を優先し、必要に応じて外部集計とコミュニティ情報を補助的に使う。`Genba仮説`ごとに支持材料、反証・留保、面接検証質問、対象地域、確認日を揃える。既存仮説に反する新情報を見つけた場合も削除せず、確度または結論を更新する。

`想定できる売り方`を追加・更新する場合は、`ops/company-selling-playbook-standard.md`を読む。3つの課題視点と4段階のnarrativeを固定順で使い、外部環境の要求を製品機能・自社roadmap・採用拡大で代用しない。

## 3. 公開候補を更新する

確認済みの変更だけを`lib/market-data.ts`へ反映する。

- 同一求人を重複登録しない
- 公式URLが生きていることを再確認する
- 日付は実際の確認日に合わせる
- 募集終了求人は即時削除ではなく、将来の履歴設計に沿って終了扱いを検討する
- スポンサー企業でも通常企業と同じ事実確認基準を使う

データ構造を変える場合は、`docs/10-website-renewal-spec.md`も更新する。

## 4. コンテンツ候補を作る

毎日作る候補:

- 変化フィード
- 新規・変更求人の短文紹介
- Harvey・Dropbox見本の骨格による`1社深掘り`のX下書きを、異なる2社で2本作る。対象は新規追加企業や当週に動いた企業へ限定せず、Genba掲載企業全体から選ぶ(詳細は[X投稿戦略](x-content-strategy.md)を参照)

毎週月曜日・木曜日・土曜日19:30（Asia/Tokyo）の配信用に作る候補:

- Genbaニュースレターの企業候補5社
- 新着・終了求人、採用変化、日本進出シグナル、海外一次情報から選定理由を作る
- 5社は原則として異なるソリューション領域、現在応募可能な企業3社以上、アンカー企業1社以下、日本未進出企業1社以下とする
- 日本未進出企業は現在応募できる会社と分離し、進出可能性・追い風・障壁を事実とGenba仮説に分ける
- 通常の編集選定では同じ企業を原則45日以内に再掲載せず、重要な求人・組織変更がある場合だけ例外とする
- スポンサー企業を含める場合は5社中最大1社とし、`広告`と`Sponsored`を明示する

「デイリータスク」では日本時間の実行曜日を確認する。月曜日・木曜日・土曜日なら、候補作成で止めず、`ops/daily-task-workflow.md`5章に従って送信可能なニュースレターを作成し、Kitへ入稿する。完成次第、Jioの確認用アドレス`js@genbajapan.com`へ直ちにテスト送信する。Jioの返信や追加承認を待たずに所定項目を検証し、合格かつ同日19:30（Asia/Tokyo）前なら、そのまま19:30に予約してから完了する。対話実行が必要だとして停止しない。テスト不合格・確認不能・認証切れ・19:30経過時だけ本配信せず、下書きを保持して報告する。

編集記事は週1〜2本を上限目安とし、記事数を埋めるために作らない。既存英語記事はアーカイブ扱いとし、新規コンテンツは日本語を基本とする。

X原稿は[X投稿戦略](x-content-strategy.md)に沿って`1社深掘り`を異なる2社で2本作成し、各本文と事実確認メモを`content/x/drafts/`へ保存する。Genbaへのリンクには同戦略のUTMを付け、リンク先とパラメータ保持を確認する。対話型およびスケジュール実行の`デイリータスク`では`ops/daily-task-workflow.md`3-1に従って、確定本文2本を`@chosenshi08`のX未投稿ドラフトにも1本ずつ保存する。投稿・予約は行わない。

## 5. 必須ガードレール

公開候補ごとに確認する。

- 公式出典がある
- 確認日がある
- 事実と分析が分離されている
- 給与・OTE・言語・勤務形態を推測していない
- 求人票・記事・画像を無断転載していない
- 非公開情報、顧客情報、個人情報、現勤務先情報を含まない
- Adyenまたは決済領域の企業を含まない
- 広告・スポンサーは明示されている
- 応募仲介、候補者提供、成功報酬に当たる処理をしていない
- 固有名詞、数字、日付、リンクを再確認した

1つでも確認できない項目があれば、その候補は公開せず、理由を報告する。

## 6. 検証する

1. `npm run validate:agents`
2. `npm run validate:playbooks`
3. `npm run build`
4. `git diff --check`
5. 変更した内部リンクと外部公式リンクを確認する
6. `git status --short`で対象外の変更が混ざっていないことを確認する

検証失敗時は公開しない。既存の正常な公開データを壊して完了扱いにしない。

## 7. 公開する

Claude Code・CodexがJioと対話しながら実行する通常セッションでは、「デイリータスク」を含め、`npm run check`成功後に今回の対象ファイルだけを明示してステージし、コミット・push・デプロイ確認まで行う。push・公開について実行ごとの確認は求めない。

X投稿、X予約、`デイリータスク`所定のテスト送信・19:30予約とGenba 300日次確認通知以外のメール配信、スポンサー連絡はこの自動公開に含めず、その回の明示承認がある場合だけ行う。対話型およびスケジュール実行の`デイリータスク`では、`@chosenshi08`の未投稿ドラフトへ2本を1本ずつ保存し、配信曜日には原稿完成直後のJio宛テスト送信と、所定テスト合格後の同日19:30予約までを、追加確認なしの必須工程として実行する。Genba 300は掲載変更の有無にかかわらず、日次確認完了後にJioだけへ通知する。Xの投稿・予約・返信・引用・再投稿、ニュースレターの別時刻配信・臨時配信・配信対象変更へは拡張しない。

公開した場合は、トップ、企業、求人、シグナル、変更対象ページの正常応答を確認する。

### 7-1. スケジュール実行(自動トリガー)時の例外

`/genba-daily`をスケジュール実行(人が都度依頼せず自動起動)する場合に限り、以下の「軽微な変更」「標準フォーマットによる新規企業追加」「基準を満たすGenba 300の入れ替え」は、実行ごとの承認を得ずに`npm run check`成功を条件に自動でpush・公開してよい(2026-08-10、2026-08-16、2026-11-03 Jio承認。`PROJECT_RULES.md`7章参照)。

**軽微な変更に該当する(自動公開してよい)**

- 公式ページ・ATSで404/掲載終了を確認できた求人を、募集終了として`hiringStatus`等へ反映する
- 内容に変更がなかった企業・求人の`lastChecked`(最終確認日)だけを更新する

**新規企業追加として自動公開してよい**

- `ops/daily-task-workflow.md`の選定配分・調査基準を満たす新規企業
- 共通の`CompanyIntelligenceProfile`・`CompanyPublicIntelligence`型と`ops/company-selling-playbook-standard.md`に従う標準企業ページ
- その新規企業と同時に公式Career・公式ATSで確認した公式求人、採用シグナル
- 上記に必要な一覧・sitemap・`llms.txt`等の既存標準導線への登録

**Genba 300の入れ替えとして自動実行してよい**

- `ops/genba-300-selection-standard.md`のスコア、点差、継続確認、確信度、1回最大3組の条件をすべて満たす一対一の入れ替え
- 除外企業を公開導線から外し、調査データは非公開の履歴として保持する変更
- `npm run check`成功後のpush・公開と、トップ、企業一覧、追加・除外企業、求人、採用シグナル、sitemap、`llms.txt`の本番確認
- 日次確認完了後、Kitのテスト送信で`js@genbajapan.com`だけへ送る確認結果。追加・除外がある日は点数・根拠・公式出典・本番確認結果を含め、掲載変更がない日は`変更なし`と確認内容を送る。確認未完了時は送信可能なら失敗理由を送り、購読者へ本配信しない

**X未投稿ドラフトへの保存として自動実行してよい**

- `ops/daily-task-workflow.md`3-1の確認手順を満たした確定本文2本を、`@chosenshi08`の未投稿ドラフトへ1本ずつ保存する
- 投稿、予約、返信、引用、再投稿は行わず、公開タイミングと最終投稿操作はJioが決める
- 認証切れ、CAPTCHA、対象アカウント不明、保存確認不能がある場合は回避操作をせず、ローカル下書きを保持して報告する

**ニュースレターのテスト・予約として自動実行してよい**

- 配信曜日の`デイリータスク`で作成した`Genba発掘`をKitへ入稿し、原稿完成後ただちにJioの確認用アドレス`js@genbajapan.com`へテスト送信する。Jioの返信・確認・承認は待たない
- `docs/11-newsletter-kit-setup.md`の毎号テストがすべて合格し、実行時点が19:30前なら、そのまま同日19:30（Asia/Tokyo）の本配信として予約する。対話実行や追加承認を条件にしない
- テスト不合格、送信・表示・リンク・配信対象・timezoneの確認不能、認証切れ、または19:30経過時は予約・本配信をせず、下書きを保持して報告する

企業固有UI、新しいデータ構造、標準外セクション、確認不能な情報、法務・利益相反上の懸念がある内容は自動公開に含めない。

**軽微な変更に該当しない(スケジュール実行でも従来通り承認が必要)**

- 既存企業への新規求人の追加(`descriptionSummary`・`genbaTake`・`compensationReality`・`desiredProfile`・`careerInsights`等の分析を伴うもの)
- 既存求人のタイトル・要件・セグメントなど内容面の変更
- 既存企業ページ(`company-public-intelligence.ts`)の分析結論・構成・内容変更
- X下書きの投稿、`デイリータスク`所定のテスト送信・19:30予約とGenba 300日次確認通知以外のニュースレター配信、その他編集コンテンツの公開

この区分に迷う変更は「軽微」に含めず、通常フロー(下書きまで作成して停止・報告)に従う。自動公開した場合も8章の報告内容を作成し、次にJioが確認できる形で残す。

## 8. 報告する

以下を簡潔に報告する。

- 追加・変更・終了した企業／求人
- 作成したコンテンツ下書き
- 使用した公式出典
- 公開しなかった候補と理由
- 検証結果
- コミット・push・本番反映の有無
- Jioの判断が必要な項目
- `Genba 300`の公開対象数・構成比、追加候補、除外候補、入れ替えペア、実装・本番確認結果、Jio宛日次確認メールの種別・送信日時・成否。条件を満たす組み合わせがなければ`入れ替えなし・変更なしメール送信済み`とする
